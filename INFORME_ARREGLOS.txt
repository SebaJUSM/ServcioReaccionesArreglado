Servicio de Reacciones - informe de arreglos y cautelas
========================================================

Origen y destino
----------------
- Se copio el proyecto original desde /root/Servicio de Reacciones hacia la carpeta de trabajo.
- La version corregida debe quedar en /root/ServcioReaccionesArreglado.

Diagnostico
-----------
- El servicio FastAPI de reacciones ya existia en app/main.py y app/api/v1/reactions.py.
- La API permitia crear, listar y eliminar reacciones, pero la validacion de usuarios/mensajes estaba simulada de forma fija.
- RabbitMQ no estaba realmente implementado en el servicio principal: solo se escribian eventos en logs.
- docker-compose.yml declaraba EVENT_BROKER_URL apuntando a rabbitmq, pero no levantaba ningun contenedor RabbitMQ.
- El manejo de errores usaba HTTPException directamente y no tenia formato uniforme.
- La base de datos no tenia una restriccion unica real para impedir duplicados bajo condiciones de concurrencia.
- La copia incluia archivos residuales :Zone.Identifier que no pertenecen al proyecto.

Arreglos realizados
-------------------
- Se agrego app/core/errors.py con errores estructurados y handlers globales para errores de aplicacion, HTTPException, validacion, SQLAlchemy y excepciones no controladas.
- Las respuestas de error ahora siguen el formato {"error": {"code": "...", "message": "...", "details": ...}}.
- Se reemplazaron errores manuales en endpoints por ResourceNotFoundError y ConflictError.
- Se agrego control de IntegrityError para responder 409 si se intenta crear una reaccion duplicada.
- Se agrego UniqueConstraint sobre message_id + user_id + reaction_type en el modelo Reaction.
- Se mejoro la validacion de entrada: message_id y user_id no pueden ser vacios, reaction_type se normaliza a minusculas y solo acepta letras, numeros, guion y underscore.
- Se implemento validacion HTTP real de mensajes y usuarios en app/services/external.py.
- Se agrego modo simulado configurable con EXTERNAL_VALIDATION_ENABLED=false para desarrollo local.
- Se implemento RabbitMQ real con aio-pika en app/services/event_producer.py: conexion robusta, exchange topic durable, mensajes persistentes, reintentos configurables y cierre limpio al apagar FastAPI.
- Se agrego health check con estado de eventos y conexion RabbitMQ.
- Se actualizo docker-compose.yml para levantar reaction-service y rabbitmq con management UI, volumen para SQLite, volumen para RabbitMQ, healthchecks y depends_on.
- Se agrego aio-pika a requirements.txt.
- Se mejoro Dockerfile con variables Python, usuario no root, carpeta /app/data y healthcheck.
- Se agrego .dockerignore.
- Se agrego .env.example con las variables principales.
- Se actualizaron notas de uso en README-ReactionService.md.
- Se limpiaron archivos :Zone.Identifier y __pycache__.

Simplificacion del despliegue
----------------------------
- Se retiraron los cuatro manifiestos de Kubernetes de k8s/: deployment.yaml, service.yaml, ingress.yaml y hpa.yaml.
- Se eliminaron las referencias a Kubernetes en los comentarios de configuracion y del endpoint /health.
- El despliegue del servicio principal se gestiona con Docker Compose (reaction-service y rabbitmq) o ejecutando FastAPI con Uvicorn.
- Se mantienen los endpoints REST, los modelos de datos, los codigos HTTP, la validacion externa y la publicacion de eventos RabbitMQ.
- Dockerfile, docker-compose.yml y requirements.txt no necesitan cambios para esta simplificacion.

Limpieza de componentes ajenos
-----------------------------
- Se eliminaron service_01/ (jugadores) y service_02/ (equipos), que pertenecian a una demo anterior y no eran parte de la API de reacciones.
- Se eliminaron api-gateway/ (GraphQL) y message_broker/ (configuracion del broker de esa demo).
- Se eliminaron populate.py y demo.gif, que solo documentaban o cargaban datos de la demo anterior.
- README.md ahora documenta el servicio de reacciones y enlaza su guia detallada.
- La unica aplicacion del proyecto esta en app/. Docker Compose conserva reaction-service y RabbitMQ, que es infraestructura para sus eventos.
- El codigo FastAPI, los endpoints REST y la configuracion Docker del servicio de reacciones se conservan.
- Se comprobo que no quedan referencias activas a la demo eliminada fuera del registro historico de este informe.
- Tras la limpieza se verificaron /health, Swagger/OpenAPI y el flujo de creacion (201), consulta (200) y eliminacion (204), con SQLite en memoria, validacion simulada y eventos deshabilitados.

Cautelas importantes
--------------------
- Docker no esta disponible en este WSL al momento de la revision. Para usar docker compose, activa la integracion de Docker Desktop con esta distro WSL.
- Por defecto EXTERNAL_VALIDATION_ENABLED=false para que el servicio pueda probarse sin microservicios externos. En produccion debe ponerse en true y configurar MESSAGES_SERVICE_URL y USERS_SERVICE_URL.
- Los servicios externos deben responder 2xx si el recurso existe y 404 si no existe. Otros codigos se tratan como error del servicio externo.
- Por defecto EVENTS_REQUIRED=false. Esto evita que una caida temporal de RabbitMQ rompa la API, pero puede dejar eventos sin publicar. Si necesitas consistencia estricta, usa EVENTS_REQUIRED=true o implementa un patron outbox.
- SQLite es suficiente para demo/desarrollo. Para produccion o alta concurrencia conviene migrar a PostgreSQL y usar migraciones con Alembic.
- Base.metadata.create_all crea tablas, pero no aplica migraciones sobre tablas existentes. Si ya existe una base reactions.db antigua, la restriccion unica podria no aplicarse hasta migrar o recrear la tabla.
- La URL de RabbitMQ por defecto usa credenciales guest/guest, adecuadas para desarrollo local, no para produccion.
- Docker Compose levanta dos contenedores: la unica API de reacciones y su broker RabbitMQ. Los servicios HTTP de usuarios y mensajes deben proporcionarse externamente al activar la validacion real.

Validaciones realizadas
-----------------------
- python3 -m compileall app: correcto.
- Parseo de docker-compose.yml con YAML: correcto; contiene reaction-service y rabbitmq.
- Prueba funcional con entorno temporal y EVENTS_ENABLED=false:

  - POST /api/v1/reactions -> 201.
  - POST duplicado -> 409 con error duplicate_reaction.
  - GET /api/v1/messages/{message_id}/reactions -> 200.
  - POST con message_id=not-found -> 404 con error message_not_found.
  - DELETE /api/v1/reactions/{reaction_id} -> 204.
